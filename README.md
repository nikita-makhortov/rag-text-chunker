# rag-chunker

Лёгкий Python-пакет и CLI-утилита для очистки текстовых документов, нарезки скользящим окном (sliding window) и оценки качества чанкинга в RAG-пайплайнах (Retrieval-Augmented Generation).

Весь проект написан исключительно на стандартной библиотеке Python (`re`, `json`, `statistics`, `argparse`, `dataclasses`, `pathlib`) без подключения тяжёлых NLP-фреймворков.

---

## 1. Зачем нужен правильный чанкинг в RAG

Если подавать сырые длинные документы напрямую в векторную базу и контекстное окно языковой модели (LLM), возникают три проблемы:

1. **Размытие эмбеддингов (Embedding Dilution):** при кодировании большого текста целиком один вектор усредняет разные темы, и поиск хуже находит точные технические факты.
2. **Эффект "Lost in the Middle":** языковые модели хуже извлекают информацию из середины длинного промпта, чем из его начала и конца.
3. **Разрыв смысловых связей:** слепая нарезка по символам режет предложения пополам — условие правила попадает в один чанк, а числовой норматив в другой.

### Движение данных внутри программы

    Сырой .txt -> TextPreprocessor.process() -> BaseSplitter.split() -> list[TextChunk] -> JSON / BenchmarkMetrics

* **`src/rag_chunker/models.py` (Модели данных):**
  * Используется декоратор `@dataclass` из стандартной библиотеки — это способ описать класс для хранения данных без ручного написания `__init__`.
  * `TextChunk` хранит один готовый чанк: `source_id` (имя документа), `index` (номер чанка), `content` (текст) и `unit_count` (сколько в нём слов или предложений). Метод `to_dict()` через функцию `asdict()` превращает объект в обычный словарь `dict` для сохранения в JSON.
  * `BenchmarkMetrics` хранит итоговые цифры сравнения стратегий для вывода в таблицу.

* **`src/rag_chunker/preprocessor.py` (Очистка текста):**
  * Класс `TextPreprocessor` принимает два флага: `keep_punctuation` (оставлять ли знаки препинания) и `lowercase` (приводить ли к нижнему регистру).
  * Метод `process(raw_text)` по очереди вызывает:
    1. `_collapse_whitespace` — заменяет все двойные пробелы, табы и переносы строк на один пробел (`re.sub(r"\s+", " ", text)`).
    2. `_filter_noise` — вырезает мусорные символы (`#`, `$`, `@`, `%`). Если `keep_punctuation=True`, оставляет базовые знаки `. , ! ?` и дефис `-`, чтобы не склеить маркировки вроде `Bodor-A3` и не потерять границы предложений.
    3. Приведение к нижнему регистру и финальную зачистку пробелов.

* **`src/rag_chunker/splitters.py` (Нарезка скользящим окном):**
  * `BaseSplitter` — родительский класс с общей логикой скользящего окна:
    * В `__init__` проверяет, что `window_size > 0` и `0 <= overlap < window_size`. Если перекрытие будет больше или равно размеру окна, шаг сдвига `stride = window_size - overlap` станет нулевым или отрицательным, и цикл застрянет на месте.
    * `_slice_windows(units)` двигает указатель `cursor` по списку токенов с шагом `stride`, берёт срез `units[cursor : cursor + window_size]` и останавливается, как только срез дошёл до конца списка.
    * `split(text, source_id)` вызывает `extract_units` (разбиение текста на элементы), режет их окнами и упаковывает в список объектов `TextChunk`.
  * `WordSplitter(BaseSplitter)` — наследник для пословной нарезки: делит текст по пробелам (`text.split()`) и убирает пунктуацию по краям слова (`.strip("!?.,-")`).
  * `SentenceSplitter(BaseSplitter)` — наследник для нарезки по предложениям: использует регулярку с проверкой назад `re.split(r"(?<=[.!?])\s+", text)`. Она режет только по пробелам после точки/восклицательного/вопросительного знака, поэтому десятичные дроби вроде `0.02 мм` или `16.5 бар` не разрываются.

* **`src/rag_chunker/evaluator.py` (Подсчёт метрик):**
  * `ChunkEvaluator` вычисляет статистику через стандартный модуль `statistics` (`mean` — среднее, `stdev` — стандартное отклонение) и две метрики качества RAG:
    * `sentence_break_rate` (**SSR**) — проверяет для каждого эталонного предложения, входит ли оно целиком хотя бы в один чанк (`sentence in chunk.content`), и считает процент разорванных предложений.
    * `redundancy_ratio` (**TRR**) — делит суммарное число юнитов во всех чанках на исходное число юнитов в документе.
  * `format_comparison` собирает из двух объектов `BenchmarkMetrics` ровную текстовую таблицу для консоли.

* **`src/rag_chunker/cli.py` (Командный интерфейс):**
  * Через стандартный модуль `argparse` создаёт две подкоманды: `split` (нарезать файл в JSON) и `benchmark` (сравнить две стратегии на одном документе). Для работы с путями и чтения/записи файлов используется `pathlib.Path`.

## 3. Быстрый старт и команды

### Установка и прогон тестов

    python3 -m venv .venv
    source .venv/bin/activate
    pip install -r requirements.txt

    pytest -v

### Запуск утилит из терминала

1. **Нарезать корпус документов в JSON-файл:**

       PYTHONPATH=src python3 -m rag_chunker split \
         --input data/sample_documents.txt \
         --output data/chunks.json \
         --strategy sentence \
         --size 3 \
         --overlap 1

2. **Запустить бенчмарк (сравнение нарезки по предложениям и по словам):**

       PYTHONPATH=src python3 -m rag_chunker benchmark --input data/large_document.txt

## 4. Метрики качества и результаты эксперимента

* **SSR (Sentence Splitting Rate, %)** — доля предложений исходного текста, которые оказались разорваны границей чанка или потеряли целостность. Чем ниже показатель, тем меньше искажённых правил.
* **TRR (Token Redundancy Ratio)** — коэффициент раздувания объёма данных из-за перекрытия окон (`1.00` — перекрытия нет; `1.48` означает `+48%` к объёму хранимых и индексируемых токенов).

### Сравнение на техническом регламенте лазерного комплекса (`data/large_document.txt`, 57 предложений)

| Метрика | По предложениям (3 / overlap 1) | По словам (100 / overlap 20) |
| :--- | :---: | :---: |
| **Всего чанков (`total_chunks`)** | `28` | `13` |
| **Средний размер (юнитов)** | `2.96` предл. | `98.92` слов |
| **Станд. отклонение (`stdev`)** | `0.19` | `3.88` |
| **Средняя длина (символов)** | `483.11` | `846.08` |
| **Разрыв предложений (`SSR`)** | `0.0%` | `100.0%` |
| **Избыточность токенов (`TRR`)** | `1.48` (+48%) | `1.23` (+23%) |

### Выводы

* Для технической документации и регламентов выигрывает **нарезка по предложениям**: ни одно правило не разрывается на стыке (`SSR = 0.0%`), что критично при извлечении числовых допусков и параметров безопасности, несмотря на умеренный рост индекса (`TRR = 1.48`).
* **Пословная нарезка** экономичнее по памяти (`TRR = 1.23`), но жёсткая отсечка каждые 100 слов и очистка пунктуации разрушают границы предложений, поэтому этот режим лучше подходит для однородных повествовательных текстов без строгих правил.
